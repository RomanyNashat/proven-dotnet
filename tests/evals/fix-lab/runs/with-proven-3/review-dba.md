## Database Review: HomeReadings (dba-reviewer)

The service has no migration and no SQL script anywhere in the repo, so there is nothing yet that can create the schema in production. I found 7 Critical, 9 Warning and 4 Suggestion findings. Skills are under /home/claude/proven-dotnet/.claude/skills/. Line numbers are from /tmp/claude-0/labruns/with-proven-3/HomeReadings. The Roslyn MCP wasn't available, so I read the files directly.

**Known-traps item, `Program.cs:7` (ValidateScopes/ValidateOnBuild): confirmed, stays info.** Production turns both checks off, and your tests run in Production, so a captive DbContext would never be caught. Nothing is broken today: `ReadingNotifier` uses `IServiceScopeFactory`, `PhotoStore` only takes `IConfiguration`, and the DbContext is Scoped. Fix: `builder.ValidateServicesInEveryEnvironment()` (`dotnet-core`, "The host").

### Critical
1. **One patient can read another's data (IDOR)** `Application/ReadingQueries.cs:12-16`. `GetAsync` filters only by `Id`. Ids are sequential ints, so any signed-in patient can walk `/readings/1..N` and read everyone's readings and notes. Fix: `.Where(r => r.Id == id && r.PatientId == patient.Id)`. Source: rules/security.md ("every lookup by ID checks ownership"), `efcore-patterns` §3.
2. **The "latest" cache is shared by all patients** `ReadingQueries.cs:32`. The key is `"readings:latest"` with no patient id, so for up to a minute every patient on that pod is shown the first caller's latest glucose reading. On top of that, a patient's own new reading doesn't show for a minute, and each pod has its own copy. Fix: drop the cache. The query is a single seek on the `(PatientId, CollectedAt)` index, well under 1 ms. If you keep it, use `$"readings:v1:latest:{patient.Id}"` and remove that key in `AddAsync`. Source: `caching` (stable, prefixed keys), rules/security.md.
3. **A high reading can be saved with no alert, and nothing ever retries it** `Application/ReadingService.cs:16-23`. The reading and its alert are two separate `SaveChangesAsync` calls. If the pod is killed, a deploy lands or the connection drops between them, the high reading is stored and no alert row exists. That is a patient-safety loss. The model also has no relationship between `CareTeamAlert.ReadingId` and `readings` (no navigation, so no FK and no index), so an orphan alert is possible too. Fix: give the alert a `Reading` navigation, or put alerts in a collection on `Reading`. EF then inserts both rows in one `SaveChangesAsync`, which is already one transaction. Configure `HasOne<Reading>().WithMany().HasForeignKey(a => a.ReadingId)`. Source: `efcore-patterns` §7 ("first ask whether one save does it"), `outbox` (same transaction).
4. **Notifier: one failure stops the whole service, every pod alerts the nurses, and a POST can be resent** `Application/ReadingNotifier.cs:15-35` and `Program.cs:20-21`.
   - No try/catch. A care-team outage, or an orphan alert (`SingleAsync` at :18 throws), escapes `ExecuteAsync`. The default `StopHost` then stops the host, so the reading API goes down and the pods restart-loop for as long as the care team is down. The first unsendable alert also stays first in line (`OrderBy(Id)`) and is hit again on every run. Fix: wrap each run in `catch (Exception ex) when (ex is not OperationCanceledException)` (`worker-patterns`, PeriodicSyncWorker), add `Attempts` and `LastError` columns to the alert (store the exception type only), and back off.
   - With more than one replica (I assumed production runs more than one), every pod selects the same `SentAt IS NULL` rows and each one POSTs them. The care team has no idempotency key, so a nurse gets one alert per pod. Fix: only one runner at a time, using `pg_try_advisory_xact_lock` as the `outbox` relay does (`postgresql-patterns` §11). Or claim rows with `FOR UPDATE SKIP LOCKED` and commit the claim before sending (`worker-patterns`, WorkClaims).
   - `AddStandardResilienceHandler()` retries POSTs by default, so a timed-out POST that actually arrived is sent again. Fix: `o.Retry.DisableForUnsafeHttpMethods()` (package is 10.0.0, which is ≥ 9.8.0). Source: `polly-resilience`.
   - Keep the save-per-row at :21: it keeps the "sent but not marked sent" window as small as possible. But run that save with `CancellationToken.None` once the POST has succeeded. Today a shutdown that cancels it re-sends the alert on the next start.
5. **`CollectedAt` from the app is rejected or stored at the wrong time** `ReadingService.cs:7,14-15`. The request is a plain `DateTime`. STJ gives `Kind=Unspecified` when the app sends no offset, and `Kind=Local` when it sends `+03:00`. Npgsql refuses both for `timestamptz` ("throws for Kind≠Utc"; on a UTC pod `Local` is refused too). The result is a 500 and a lost reading. Your tests pass only if they send `Z`. Fix: make it a `DateTimeOffset`, require an offset, and store `.UtcDateTime`. Also reject times in the future. Source: `postgresql-patterns` §2.
6. **The meter value is parsed under `ar-SA`** `ReadingService.cs:14`. `decimal.Parse(request.Value)` uses the culture `LanguageMiddleware.cs:13-14` sets. Under `ar-SA` (where ICU gives `٫` as the decimal separator), `"12.5"` fails with a 500. Under `en-US`, a meter showing `"5,6"` parses as **56** with no error, and that crosses `AlertLevel`, so a nurse gets a false alert. Arabic-Indic digits (`١٢٫٥`) never parse. Fix: parse with `NumberStyles.AllowDecimalPoint, CultureInfo.InvariantCulture` after converting Arabic-Indic digits and `٫`/`,` to ASCII, then check the range (for example 0.5–40 mmol/L). Return 400 when it doesn't parse. Source: `localization` §1 ("machine values use InvariantCulture"), csharp-standards ("never let ar-SA become the formatting culture").
7. **`NationalId` comes from the request body, not the caller's identity** `ReadingService.cs:14`, `ReadingNotifier.cs:19`. A patient can post a reading carrying another person's national ID. The alert then reaches a nurse under the wrong patient. Fix: take the national ID from the token claim or the patient record. Don't store it on every reading row: the notifier can look it up per patient. Source: rules/security.md (PII). Hand to the security-reviewer too.

### Warnings
1. **Unbounded column** `Infrastructure/ReadingsDbContext.cs` (Reading block, no line for `Notes`). `Notes` has no `HasMaxLength`, so it becomes `text`, which is a hard ban. Fix: `.HasMaxLength(500)`. Source: rules/efcore-rules.md, `efcore-patterns` §2.
2. **No migration and no script**. The repo has no Migrations folder, so production has nothing that creates `readings` or `care_team_alerts`. Fix: generate an up/down pair with `/migrate`, starting with `SET lock_timeout = '5s';`. The tables are new, so plain `CREATE INDEX` is fine in this script. Later indexes need `IsCreatedConcurrently()` and must be scripted without `--idempotent`. Source: rules/efcore-rules.md, `postgresql-patterns` §5.
3. **"Today" is the UTC day** `ReadingQueries.cs:21-22`. For a Riyadh patient the chart switches days at 03:00 local, so between 00:00 and 03:00 it shows yesterday's readings. Fix: work out local midnight in `RiyadhTime.Zone` and convert it to a UTC range. Source: `efcore-patterns` §9 ("a local day is a UTC range"), `localization` §7.
4. **Connection pool not sized** `appsettings.json:3`. The connection string sets no `Maximum Pool Size`, `Timeout` or `Command Timeout`. With Npgsql's default of 100 per pod, `pods × 100` passes PostgreSQL's default `max_connections` of 100 at the second pod. There is also no `EnableRetryOnFailure`. Fix: `Maximum Pool Size=20;Timeout=15;Command Timeout=30`, agreed with the DBA, plus `EnableRetryOnFailure(3)`. Source: `postgresql-patterns` §3. The checked-in password belongs to the security-reviewer.
5. **Index doesn't fit the notifier's query** `ReadingsDbContext.cs:31`. The query is `WHERE "SentAt" IS NULL ORDER BY "Id" LIMIT 50`. A plain index on `SentAt` grows with every alert ever sent. Fix: a partial index (below). Source: rules/performance.md.
6. **N+1 in the notifier** `ReadingNotifier.cs:18`. Each alert loads its reading in a separate query: up to 51 round trips per minute per pod. Fix: one projected query that joins alerts to readings and selects `(alert, NationalId, Value, CollectedAt)`. Source: `efcore-patterns` §9.
7. **No idempotency on POST /readings** `Api/ReadingEndpoints.cs:11`. A mobile retry on a bad network stores the reading twice and raises two alerts. Fix: a client-generated idempotency key, stored as `uuid` with a unique index, and insert with `ON CONFLICT DO NOTHING`. A GUID is allowed here because the id is created outside the database. Source: `postgresql-patterns` §8, rules/efcore-rules.md.
8. **Photo row stores an absolute path on a local volume** `Infrastructure/PhotoStore.cs:12-15`, `ReadingsDbContext.cs:22`. The row holds the client's file name inside a pod-local path. That path can pass the 260 limit, and when it does the file is already written and the save then fails. Other pods may not see the volume. Fix: object storage, with the row keeping a bounded key such as `{readingId}/{uuid}.jpg`. Source: rules/efcore-rules.md (no binary data, the row keeps the key). The path traversal is the security-reviewer's.
9. **Patient data in logs and error responses** `ReadingService.cs:25`, `Api/ErrorMiddleware.cs:16`. `{@Reading}` writes the national ID, glucose value and notes to Elastic, and Npgsql/DB exception messages go back to the client. Fix: log the id only, and return ProblemDetails. Source: rules/security.md. Cross-area; I've only noted it here.

### Suggestions
- Column names are PascalCase (`"PatientId"`) while table names are snake_case. Any Dapper or DBA SQL then has to quote every column. Pick snake_case now, before the first script, with `HasColumnName` or `UseSnakeCaseNamingConvention()` (`postgresql-patterns` §2).
- `LatestAsync` orders by `CollectedAt` alone, so two readings with the same timestamp come back in any order. Add `.ThenByDescending(r => r.Id)` (`efcore-patterns` §9, unique order).
- `Unit` is free text, but `NeedsAlert` compares against a mmol/L threshold, so every mg/dL reading would alert. Use an allowlist of units and convert to mmol/L before saving.
- `/health/live` runs the DbContext check (`Program.cs:31,40`), so a database blip makes Kubernetes restart every pod. Keep the DB check on `/health/ready` only.

### Index recommendations
- `CREATE INDEX ix_care_team_alerts_pending ON care_team_alerts ("Id") WHERE "SentAt" IS NULL;` serves `ReadingNotifier.cs:15`. In EF: `HasIndex(a => a.Id).HasFilter("\"SentAt\" IS NULL")`. Replaces `ReadingsDbContext.cs:31`.
- `CREATE INDEX ix_care_team_alerts_reading_id ON care_team_alerts ("ReadingId");` for the new FK.
- Keep `(PatientId, CollectedAt)`. It serves `ReadingQueries.cs:24` and `:36`. Unique index on the idempotency key if you add one (Warning 7).

### Migration safety
This is a greenfield schema with no migration, so nothing is at risk for N-1 yet. Make the first script create both tables, the FK and the indexes, with up and down scripts, and review it before the first deploy.
