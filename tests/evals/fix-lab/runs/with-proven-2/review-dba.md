## Database Review: HomeReadings (dba-reviewer)

I read all 16 files in the service. No Roslyn MCP was available, so I traced the code by hand, which is enough for a project this size. There are **no migrations in the folder**, so I reviewed the schema from the model in `ReadingsDbContext.cs`.

**Known-traps scan, `Program.cs:7` (ValidateScopes/ValidateOnBuild): confirmed, info.** This is in my area because it covers DbContext lifetime. Nothing is captive today: `ReadingNotifier` is a singleton but uses `IServiceScopeFactory`, and the typed client, DbContext and services are resolved per scope. But your tests run in Production, so the lifetime check never runs anywhere. Turn on both flags (`dotnet-core`, Rules).

### Critical
1. **Cross-patient leak.** `Application/ReadingQueries.cs:32`: the cache key `"readings:latest"` is the same for everyone. The first patient's latest reading is served to every patient on that pod for a minute. This is a PHI leak on the endpoint every app start calls. **Fix:** key per patient (`$"readings:v1:latest:{patient.Id}"`) and remove that key in `AddAsync` (`caching`, keys; `rules/security.md`).
2. **IDOR.** `Application/ReadingQueries.cs:12-16`: `GetAsync` filters only by `Id`. The ids are sequential ints, so any patient can read any reading. **Fix:** add `&& r.PatientId == patient.Id`, or a named owner query filter that reads a context member (`efcore-patterns` §3; `rules/security.md`). Security will likely report this too.
3. **A high reading can be saved with no alert.** `Application/ReadingService.cs:16-23`: the reading and the alert are saved in two separate `SaveChangesAsync` calls, both using the request's `ct`. A client abort, a pod kill or a database error between them commits the reading and loses the alert, and the nurse is never told. **Fix:** save once. Add a navigation (`Reading.Alerts` or `CareTeamAlert.Reading`) so EF inserts both in one transaction (`efcore-patterns` §7, "First ask whether one save does it").
4. **One failed run stops the whole service.** `Application/ReadingNotifier.cs:30-37`: `ExecuteAsync` has no try/catch. A care-team 5xx, a database blip, or an orphan alert makes `SingleAsync` (`:18`) throw. That faults the worker, and the default `StopHost` stops the pod. The bad alert is lowest `Id`, so it comes first on every start, which means a crash loop and no alerts go out. **Fix:** catch with `when (ex is not OperationCanceledException)` around each run, and handle each alert's failure on its own: record the attempt and stop or skip (`worker-patterns`, periodic worker; `outbox`, relay).
5. **Duplicate alerts to nurses.** CareTeam has no idempotency key, and duplicates come in three ways:
   - (a) `Program.cs:20-21`: `AddStandardResilienceHandler` retries POSTs by default. Fix: `o.Retry.DisableForUnsafeHttpMethods()` (package 10.0.0 ≥ 9.8, so this works) (`polly-resilience`).
   - (b) `ReadingNotifier.cs:15`: there is no single-runner lock, so every replica reads the same 50 unsent rows and sends each one. Fix: wrap the run in a transaction with `pg_try_advisory_xact_lock` and keep the batch small (`outbox` relay; `postgresql-patterns` §11).
   - (c) `ReadingNotifier.cs:21`: `SaveChangesAsync(ct)` runs after a successful POST. On shutdown, `ct` is already cancelled, so `MarkSent` is lost and the alert is sent again after restart. Fix: save the mark with `CancellationToken.None` once the POST has succeeded.

   Some duplication remains possible after these fixes (a crash between the POST and the save), so document it. Saving after each alert is the right choice here. Do not batch these saves into one, because that widens the window for duplicates.
6. **Unbounded column.** `Domain/Reading.cs:30` with `ReadingsDbContext.cs:13-24`: `Notes` has no `HasMaxLength`, so it becomes `text`. This breaks the hard ban (`rules/efcore-rules.md`; `postgresql-patterns` §1). **Fix:** `HasMaxLength(500)` (or whatever the product agrees), plus request validation. Fixing it before the first deploy costs nothing. After deploy, narrowing the column rewrites the table.
7. **The alert can carry another person's national ID.** `ReadingService.cs:14` takes `NationalId` from the request body, not from the authenticated patient. Nothing checks it against `patient.Id`, and the notifier sends it to the care team (`ReadingNotifier.cs:19`). A typo or a forged body sends a nurse an alert for someone else, and every reading row stores a duplicate copy of the national ID. **Fix:** look it up from the patient record or token claims when sending, and drop the column (`rules/security.md`, data protection).

### Warnings
1. `ReadingService.cs:15` writes `CollectedAt` as the client sent it. A `+03:00` or offset-less timestamp deserializes as `Kind=Local` or `Unspecified`, Npgsql refuses it, and the save returns a 500. This blocks every save if the Riyadh app sends local time. **Fix:** require `Z`, or take a `DateTimeOffset` and convert with `.UtcDateTime` (`postgresql-patterns` §2).
2. `ReadingService.cs:14`: `decimal.Parse(request.Value)` runs under `CurrentCulture`, which `LanguageMiddleware` sets to `ar-SA`. With Arabic separators, "11.5" can fail to parse (500). Under `en-US`, "11,5" parses as 115. Out-of-range values overflow `numeric(6,2)`. `Unit` is accepted as any string, but `AlertLevel` assumes mmol/L, so mg/dL readings would all alert. **Fix:** parse with `InvariantCulture` and `NumberStyles.AllowDecimalPoint`, validate the range, and allowlist the unit (`localization`, rule 1 and the checklist).
3. `ReadingQueries.cs:21-22`: "today" is the UTC day. Riyadh is UTC+3, so for three hours each night the chart shows the wrong day, and readings taken 00:00-03:00 local land on the previous day. **Fix:** build the range from Riyadh midnight, then `ToUniversalTime()` (`efcore-patterns` §9, "A local day is a UTC range"; `localization` §7 `RiyadhTime`).
4. **N+1.** `ReadingNotifier.cs:18` runs one `SingleAsync` per alert, up to 51 round trips a minute. **Fix:** a single join projection of `(alert, NationalId, Value, CollectedAt)`. Also, `ReadingId` (`ReadingsDbContext.cs:25-32`) has no FK, no index and no unique constraint, so orphan alerts and duplicate alerts per reading are both possible.
5. `Program.cs:11`, `appsettings.json:3`: the connection string sets no `Maximum Pool Size` (Npgsql defaults to 100 per pod) and no `Timeout` or `Command Timeout`. `pods × pool` must fit under `max_connections`, which defaults to 100. Agree the number with the DBA (`postgresql-patterns` §3).
6. `Program.cs:31,40-41`: the DbContext check is mapped to `/health/live` as well as `/health/ready`, so a database blip restarts every pod. Use tag predicates so liveness doesn't check the database (`kubernetes-dotnet`).
7. `ReadingsDbContext.cs:22` with `PhotoStore.cs:12`: `PhotoPath` is `varchar(260)` but holds the root + id + the client's file name. A long file name makes `SaveChanges` fail after the file is already written, leaving an orphan file. **Fix:** store a short key you generate, not the client name (which also has a path-traversal problem, a security issue). A local volume also isn't shared across pods; use object storage (`rules/efcore-rules.md`, binary rule).

### Suggestions
- `ReadingQueries.cs:37`: two readings with the same `CollectedAt` make "latest" nondeterministic. Add `.ThenByDescending(r => r.Id)`.
- `ReadingsDbContext.cs`: tables are snake_case but columns are PascalCase, so every hand query needs quotes (`"PatientId"`). Pick one convention before the first script (`postgresql-patterns` §2).
- Outside my area, worth passing on: `ReadingService.cs:25` logs `{@Reading}` (national ID, notes and value go to the logs; `pii-masking`). `ErrorMiddleware.cs:16` returns `ex.Message` and the inner message, which exposes Postgres error text (`rules/security.md`).

### Index Recommendations
- `CREATE INDEX ix_care_team_alerts_pending ON care_team_alerts ("Id") WHERE "SentAt" IS NULL;` replaces the full index on `SentAt` (`ReadingsDbContext.cs:31`), which keeps growing with sent rows. In EF: `HasIndex(a => a.Id).HasFilter("\"SentAt\" IS NULL")`. Serves `ReadingNotifier.cs:15`.
- `CREATE UNIQUE INDEX ux_care_team_alerts_reading_id ON care_team_alerts ("ReadingId");` plus an FK to `readings`. This gives one alert per reading and serves the join from Warning 4.
- The existing `(PatientId, CollectedAt)` index serves today, latest and photo lookups. Optionally extend it with `Id` to cover the tie-break.

### Migration Safety
There are no migrations yet. Generate the up/down pair as reviewed scripts with `SET lock_timeout` at the top. Both tables are new, so a plain `CREATE INDEX` is fine for this first release. Fix `Notes` and add the FK, unique index and partial index now, while both tables are empty. After go-live, a new index needs `IsCreatedConcurrently()`, scripted without `--idempotent`, and an FK is added `NOT VALID`, then validated (`postgresql-patterns` §5). Nothing in the app calls `Migrate`/`EnsureCreated`, which is correct.
