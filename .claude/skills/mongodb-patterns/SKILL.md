# MongoDB Patterns

**MongoDB's own official guidance is the standard here.** This skill applies it to a .NET stack.

The code marked as a sample runs in CI (`tests/SkillSamples.Tests/Mongo`) against MongoDB 7 as a replica
set, and the mongosh scripts are run as they are, with `mongosh`. Every claim marked *tested* is a test
there.

## 1. Rules

| Rule | Why |
|------|-----|
| `_id` is the default **`ObjectId`** | 12 bytes, time-ordered, generated by the driver: the MongoDB default, and in the spirit of "keep GUIDs minimal". A GUID only for an ID created outside MongoDB |
| One `MongoClient` per application, singleton | It owns the connection pool; one per request exhausts connections |
| **Never log command documents** | A command carries the whole document: patient data. Record the command name and duration only (§2) |
| **Validators and indexes ship as reviewed scripts** | Same rule as SQL migrations: the app never changes the database's shape at startup. The app may *check* indexes exist and warn |
| Every lookup by ID checks ownership | `ObjectId`s are partly predictable (time + counter): the same IDOR rule as SQL (`rules/security.md`) |
| Keyset paging, not skip/limit, on anything that grows | §6; skip reads and drops every skipped document, and repeats one when a new one arrives (tested) |
| Transactions use the callback API, with nothing outside MongoDB inside it | It retries transient errors by running the callback again (tested) |

## 2. Connection and serialization (driver 3.x)

<!-- sample: tests/SkillSamples.Tests/Mongo/MongoSetup.cs -->
```csharp
public static class MongoSetup
{
    public static IServiceCollection AddMongo(this IServiceCollection services, IConfiguration config, string applicationName, string database)
    {
        MongoConventions.Register();
        services.AddSingleton<IMongoClient>(_ =>
        {
            var settings = MongoClientSettings.FromConnectionString(
                config.GetConnectionString("MongoDB") ?? throw new InvalidOperationException("ConnectionStrings:MongoDB is missing."));
            settings.ApplicationName = applicationName;
            settings.MaxConnectionPoolSize = 50;   // × pods: agree the fleet total with the DBA
            settings.ServerSelectionTimeout = TimeSpan.FromSeconds(10);

            // Command name and duration only. e.Command and e.Reply hold whole documents: patient data.
            settings.ClusterConfigurator = cluster => cluster
                .Subscribe<CommandSucceededEvent>(e => MongoMetrics.Record(e.CommandName, e.Duration, failed: false))
                .Subscribe<CommandFailedEvent>(e => MongoMetrics.Record(e.CommandName, e.Duration, failed: true));

            return new MongoClient(settings);   // one per application: it owns the connection pool
        });
        services.AddSingleton(sp => sp.GetRequiredService<IMongoClient>().GetDatabase(database));
        return services;
    }
}

public static class MongoConventions
{
    private static int _registered;

    // Once per process, before any collection is used: a type's class map is built the first time it's
    // serialized, and a convention registered after that doesn't change it.
    public static void Register()
    {
        if (Interlocked.Exchange(ref _registered, 1) == 1)
        {
            return;
        }

        ConventionRegistry.Register("house", new ConventionPack
        {
            new CamelCaseElementNameConvention(),
            new IgnoreExtraElementsConvention(true),            // documents with a removed field still load
            new EnumRepresentationConvention(BsonType.String),
        }, _ => true);

        // Driver 3.x has no default Guid format and refuses to write a Guid until one is set.
        BsonSerializer.TryRegisterSerializer(new GuidSerializer(GuidRepresentation.Standard));
    }
}

public static class MongoMetrics
{
    public const string MeterName = "Samples.MongoDB";
    private static readonly Meter Meter = new(MeterName);
    private static readonly Histogram<double> Duration = Meter.CreateHistogram<double>("mongodb.command.duration", unit: "ms");

    public static void Record(string command, TimeSpan duration, bool failed) =>
        Duration.Record(duration.TotalMilliseconds, new("command", command), new("failed", failed));
}
```

- The metrics carry the command name and an outcome, nothing else (tested: an insert and a find are
  recorded, and the only tags are `command` and `failed`).
- **Register conventions before any collection is used.** A type's class map is built the first time it is
  serialized; a convention registered after that doesn't apply to it (tested).
- `IgnoreExtraElementsConvention`: a document that still has a field the class dropped loads (tested).

**Driver 3.x changes that break 2.x code:**
- A `Guid` can't be written until a format is set: the default serializer refuses (tested). Register
  `GuidRepresentation.Standard` once, as above.
- `decimal` is stored as `Decimal128` (tested); 2.x stored a string.
- LINQ: a `Select` that calls your own C# method throws `ExpressionNotSupportedException` (tested). Project
  to fields, then shape the result after `ToListAsync`. `IMongoQueryable` is gone; queries are `IQueryable`.

## 3. Schema design (the official approach)

Design for how the data is **read**, not for normal form. Data that is read together is stored together.

**Embed or reference:**
| Relationship | Default |
|--------------|---------|
| One-to-few, always read with the parent | **Embed** |
| One-to-many that grows without limit | **Reference**: a separate collection with the parent's `_id` |
| Many-to-many | Reference (arrays of `_id`s on the side that is queried) |
| Changes often and is read on its own | Reference |

**The 16 MB document limit** is the hard wall. **Never embed an unbounded array** (a user's notifications,
a device's readings): it grows until writes fail.

**The official patterns — reach for these by name:**
| Pattern | Use it when |
|---------|-------------|
| **Extended reference** | You keep joining for the same few fields: copy those fields (e.g. the patient's display name) into the referencing document |
| **Subset** | A document's array is large but screens show the latest N: embed the N, keep the rest in another collection |
| **Bucket** | Many small time-based records (vitals, steps): one document per series per hour/day |
| **Computed** | A value is read far more than its inputs change: store the result, update on write |
| **Outlier** | A few documents are huge: flag them and overflow to extra documents |
| **Schema versioning** | The shape changes: add `schemaVersion`, read both versions, migrate lazily or in a batch job |
| **Polymorphic** | Similar-but-different documents in one collection: a discriminator field |

<!-- sample: tests/SkillSamples.Tests/Mongo/Notification.cs -->
```csharp
public sealed class Notification
{
    public ObjectId Id { get; init; } = ObjectId.GenerateNewId();
    public int SchemaVersion { get; init; } = 2;
    public required int UserId { get; init; }            // the SQL user's int key
    public required string Title { get; init; }          // the validator caps it at 200
    public bool IsRead { get; init; }
    public required DateTime CreatedAt { get; init; }    // a BSON date, UTC; read back as DateTimeKind.Utc
    public List<DeliveryAttempt> Attempts { get; init; } = [];   // bounded: at most 5, the validator checks
}

public sealed record DeliveryAttempt(DateTime At, string Outcome);
```

Dates are stored as BSON dates and come back as `DateTimeKind.Utc` (tested). Write UTC from `TimeProvider`.

## 4. Validation: the database checks the shape

MongoDB accepts any shape unless told otherwise. A `$jsonSchema` validator is the equivalent of column
types and lengths, and since the SQL column rules cap strings, strings are capped here too. Bounded arrays get a
`maxItems`. Ship it as a reviewed script:

<!-- sample: tests/SkillSamples.Tests/Mongo/scripts/notifications-validator.js -->
```javascript
// db-scripts/mongo/notifications-validator.js: run by the pipeline/DBA with mongosh. Safe to run again.
const validator = { $jsonSchema: {
  bsonType: "object",
  required: ["userId", "title", "createdAt", "schemaVersion"],
  properties: {
    userId:        { bsonType: "int" },
    title:         { bsonType: "string", maxLength: 200 },
    isRead:        { bsonType: "bool" },
    createdAt:     { bsonType: "date" },
    schemaVersion: { bsonType: "int", minimum: 1 },
    attempts:      { bsonType: "array", maxItems: 5 }
  }
}};

// collMod fails on a collection that doesn't exist yet: a new database gets createCollection instead.
if (db.getCollectionNames().includes("notifications")) {
  const result = db.runCommand({
    collMod: "notifications",
    validator: validator,
    validationLevel: "moderate",   // a document that is already invalid can still get unrelated updates
    validationAction: "error"
  });
  if (result.ok !== 1) throw new Error(JSON.stringify(result));
} else {
  db.createCollection("notifications", { validator: validator, validationLevel: "moderate", validationAction: "error" });
}
```

- Tested: the class above passes it; a 201-character title and a sixth delivery attempt are refused
  (error 121); the script runs on a new database and again on an existing one.
- `collMod` alone fails on a collection that doesn't exist yet (tested), which is why the script creates it
  on a new database.
- `moderate`: a document that was already invalid can still be updated, while new invalid documents are
  refused (tested). Turning a validator on doesn't break updates to old data; fix the old data separately.

## 5. Indexes

**Compound index order follows ESR: Equality, Sort, Range** (the official rule).

<!-- sample: tests/SkillSamples.Tests/Mongo/scripts/notifications-indexes.js -->
```javascript
// db-scripts/mongo/notifications-indexes.js: run by the pipeline/DBA with mongosh. Running it again does
// nothing: createIndex with the same name and keys is a no-op. On a large collection the build loads the
// primary, so the DBA picks the window.

// ESR, Equality then Sort then Range. The user's notifications, newest first, after a cursor:
//   find({ userId: X, _id: { $lt: cursor } }).sort({ _id: -1 })
db.notifications.createIndex({ userId: 1, _id: -1 }, { name: "ix_userId_id" });

// Only unread documents are in this index, so the unread count stays cheap however many are read. A query
// uses it only when its filter includes isRead: false.
db.notifications.createIndex({ userId: 1 }, { name: "ix_unread_userId", partialFilterExpression: { isRead: false } });

// TTL: deletes each document 90 days after createdAt. In healthcare that is a retention policy: agree it first.
db.notifications.createIndex({ createdAt: 1 }, { name: "ix_ttl_90d", expireAfterSeconds: 7776000 });
```

- Running the script again is a no-op (tested).
- The paging query in §6 runs on `ix_userId_id` with no in-memory `SORT` stage, examining exactly the 10
  documents it returns (tested with `explain("executionStats")`). Check any slow query the same way: `IXSCAN`,
  not `COLLSCAN`, no `SORT`, and `totalDocsExamined` close to `nReturned`.
- A partial index is used only by a query whose filter includes its condition: a query on `userId` alone
  never considers `ix_unread_userId` (tested).
- **In healthcare, a TTL index is a retention policy.** Don't add one without the agreed retention period.
- The app may compare `ListIndexes` with what it expects and log a warning. It never creates them.

## 6. Queries and paging

<!-- sample: tests/SkillSamples.Tests/Mongo/NotificationQueries.cs -->
```csharp
public sealed class NotificationQueries(IMongoDatabase db)
{
    private readonly IMongoCollection<Notification> _notifications = db.GetCollection<Notification>("notifications");

    // Keyset paging on _id, newest first, served by ix_userId_id (Equality on userId, then Sort and Range on _id).
    // The next page starts after the last _id the caller saw: a notification that arrives between two pages
    // doesn't repeat an item, and page 50 costs what page 1 costs. Skip would read and drop every skipped one.
    public async Task<IReadOnlyList<Notification>> GetPageAsync(int userId, ObjectId? after, int size, CancellationToken ct)
    {
        var filter = Builders<Notification>.Filter.Eq(n => n.UserId, userId);
        if (after is { } last)
        {
            filter &= Builders<Notification>.Filter.Lt(n => n.Id, last);
        }

        return await _notifications.Find(filter)
            .SortByDescending(n => n.Id)
            .Limit(size)
            .ToListAsync(ct);
    }
}
```

Tested: 25 notifications in pages of 10 come back newest first, each once. When one arrives between page 1
and page 2, keyset page 2 has no repeats, while `Skip(10)` repeats the last item of page 1.

- **Project** to the fields the screen needs: `Projection.Include(...)` or a LINQ `Select` of fields.
- **Aggregation:** `$match` (on indexed fields) and `$sort` first, `$project` early. `$lookup` is a join:
  needing it on a hot path usually means an extended reference belongs in the document.
- Bulk writes: `BulkWriteAsync` with `IsOrdered = false` for independent writes.

## 7. Transactions: the callback API

Multi-document transactions need a replica set. A single-document update is already atomic, which is one
more reason to embed what changes together.

`outbox` has the tested example (`BookingService`: an appointment and its outbox message in one
transaction). The rules:
- **The callback can run more than once.** On a transient error the driver runs the whole callback again
  (tested with a server fail point: two runs, one committed write). So nothing in it may act outside
  MongoDB: no HTTP calls, no Kafka messages. Use the outbox.
- Keep it short: the server aborts transactions after 60 seconds by default.
- **Durability:** the default write concern is `majority` (tested). Don't lower it for patient data. Read
  from the primary when the caller must see its own write; secondaries lag.

## 8. Change streams

<!-- sample: tests/SkillSamples.Tests/Mongo/NewNotificationsWatcher.cs -->
```csharp
public interface INotificationHandler
{
    Task HandleAsync(Notification notification, CancellationToken ct);
}

public sealed class NewNotificationsWatcher(IMongoDatabase db, ResumeTokens tokens, INotificationHandler handler) : BackgroundService
{
    public const string Stream = "notifications.inserts";
    private readonly IMongoCollection<Notification> _notifications = db.GetCollection<Notification>("notifications");

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var options = new ChangeStreamOptions { StartAfter = await tokens.GetAsync(Stream, stoppingToken) };
        var pipeline = new EmptyPipelineDefinition<ChangeStreamDocument<Notification>>()
            .Match(c => c.OperationType == ChangeStreamOperationType.Insert);   // an insert carries the full document

        using var cursor = await _notifications.WatchAsync(pipeline, options, stoppingToken);
        while (await cursor.MoveNextAsync(stoppingToken))
        {
            foreach (var change in cursor.Current)
            {
                // No catch here. A failure stops the service, and the restart resumes from the last saved
                // token, so the failed event comes round again. Catching, logging and carrying on would save
                // the next event's token and lose this one for good. Retry transient errors inside the
                // handler; send a document that can never succeed to a dead-letter collection by its _id.
                await handler.HandleAsync(change.FullDocument, stoppingToken);
                await tokens.SaveAsync(Stream, change.ResumeToken, stoppingToken);   // only after it's handled
            }
        }
    }
}
```

`ResumeTokens` (in the same file) keeps the last handled token per stream in a `resumeTokens` collection.

- Tested: stopped and started again, the watcher gets exactly what arrived while it was down, and nothing
  twice.
- Tested: when handling fails, the watcher stops without saving that event's token, and the restart gets
  the failed event again, then the rest.
- If the saved token has fallen off the oplog, resuming fails (`ChangeStreamHistoryLost`) and a full resync
  is needed: alert on it, and size the oplog for the longest outage you expect.

## 9. Patient data

- Field-level encryption for the most sensitive fields: **Queryable Encryption** (equality and range queries
  on encrypted fields) or **CSFLE**. As far as we know, *automatic* encryption needs Enterprise or Atlas;
  *explicit* encryption works on Community. Confirm the edition before designing on it.
- No patient data in collection names, index names, or `_id`s.

## 10. Testing

Transactions and change streams need a **replica set**, so tests use one too: Testcontainers'
`MongoDbBuilder("mongo:7").WithReplicaSet()` (`testing-integration` §5). A fresh database name per test
class, dropped afterwards, keeps tests apart. Run the real validator and index scripts in the tests, so a
query that only works without them fails there.

## 11. EF Core provider: when (not) to use it

`MongoDB.EntityFrameworkCore` gives simple CRUD with `DbContext`, but (as far as we know; not tested here)
no migrations, foreign keys, time-series collections or Atlas Search, and limited projections. **Default to
the driver.** Use the provider only for a simple CRUD service where the team wants the EF programming model.
